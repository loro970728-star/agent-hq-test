## 二、遗留问题

### 🔴 P1 — §3 第 34/35 行与新规则仍然冲突

**这是 v1.1 修复不彻底留下的**：新增了第 37 行的 status 行规则，但**紧邻的第 34、35 行还是旧文字**。

现文（`AGENTS.md` §3）：

```
- Codex 只写 `work/codex/<任务编号>/`，不碰其他目录。
- Claude Code 只写 `work/claude-code/<任务编号>/`，不碰其他目录。
```

同节后续又要求：

| 出处 | 要求 |
|---|---|
| §3 第 36 行 | 产出方还要写 `evidence/<任务编号>/` |
| §3 第 37 行 | 还要写 `inbox/` 任务文件的 status 行 |
| §4 | 复核打回时还要往任务**正文**追加 `review: rejected` 行 |

**冲突点**：一个只做字面理解的 agent 读到第 34/35 行，会认为自己**连 `evidence/` 和 status 行都不能碰** —— 而这正是任务 T001 明确要求产出的东西。

**风险等级**：高。Codex 进场后可能因为「不碰其他目录」而不敢写 `evidence/T001/`，导致任务卡在验收标准第 3 条。

**建议改法**（把「产出目录」与「授权例外」分开写）：

```markdown
- Codex 的**执行产出**只写在 `work/codex/<任务编号>/`；除本公约
  明确授权的 `evidence/<任务编号>/` 和任务文件的 status 行外，不碰其他目录。
- Claude Code 的**复核意见**只写在 `work/claude-code/<任务编号>/`；除
  `evidence/<任务编号>/`、任务文件的 status 行、以及打回时追加的 `review:` 行外，
  不碰其他目录。
```

### 🟢 P3 — `review: rejected` 行在返工通过后的处理未定义

§4 规定打回时在任务正文追加 `review: rejected（原因）`，但**没说返工通过后这行怎么办**。

结果可能：同一份任务文件里同时留着 `review: rejected` 和最终 `reviewed`，后来的人分不清哪个是最终结论。

**风险等级**：低。不影响流程推进，但影响可读性。

**建议二选一，并写进公约**：

- **A（推荐）**：保留 `rejected` 行当审计痕迹，复核通过时在其下追加 `review: resolved`（或 `review: passed`）
- **B**：复核通过时删除 `rejected` 行
