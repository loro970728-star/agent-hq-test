## 1. 「错判」风险：同意，证据必要但还不够

熔断能发现程序失败，不能证明结论正确。Claude Code 举的 `grep` 漏掉反引号的例子说明：即使记录了命令和空输出，命令本身也可能没覆盖目标文本。

建议 V2 规定每项验收结论都对应可复核证据：被检查的提交 SHA 与文件路径、命令原文、标准输出和错误、退出码、以及人工可打开的相关 diff。对于「不存在旧文字」一类否定结论，再做一次范围更宽的搜索并直接检查目标文件；如果两项检查冲突或结果含糊，保持 `done`，交给人工复核。固定脚本只验证证据存在、路径与状态合法，不能把模型的「通过」一句话当作正确性证明。

首次试跑建议让无头复核只生成报告草稿，不自动写 `reviewed`。积累足够的对照样本后，再决定哪些验收项能由确定性检查自动放行；其余继续人工确认。

## 2. Codex 有无头模式，但自动认领应另设门槛

有。OpenAI 官方文档提供 `codex exec` 非交互模式，可用于脚本和定时任务，支持受限沙箱、JSONL 事件和结构化输出。本机已确认 `codex-cli 0.148.0`，`codex exec --help` 列有 `--sandbox`、`--json` 和 `--output-schema`。这证明有可调用入口；尚未对本机登录状态、代理环境及一次完整无头任务做验收。

可行的 V2 扩展是：Lo 或小咩创建任务时明确标记「允许自动认领」；watcher 只对该标记且状态为 `todo` 的无害测试任务触发 `codex exec`。Codex 在独立、受限的克隆中工作；外层脚本先核对远端任务仍为 `todo`，再按公约单独提交 `in_progress`，推送失败就停下来重新读取，避免双重认领。产出、证据、状态提交和路径白名单仍由外层校验。第一版先保持 Lo 点火，待 `done → reviewed` 这半条流水线稳定后再测试自动认领。

参考：[OpenAI 官方非交互模式文档](https://learn.chatgpt.com/docs/non-interactive-mode)。

## 3. 合并两份方案时的三个细节

1. **3 分钟轮询可作为试跑值。** 无更新时只做 Git 检查；先测实际延迟、失败率和网络请求量，再定长期间隔。
2. **路径检查应在推送前后各一次。** 无头进程不得持有推送凭据；外层脚本先验证暂存区及拟提交的 file list，再提交推送。推送后再核对远端提交的 file list，作为审计和异常告警。仅在推送后检查只能发现越界，已经来不及阻止。
3. **`Claude Code-auto` 作为审计标签可以采纳。** 它应由自动化专用克隆的 `git config --local` 设置，并在首次提交后核对 `git log`。身份名称本身不隔离权限；实际写入范围仍由独立克隆、受限执行环境和外层白名单控制。

自动化代码可以另放 `agent-ops`。T001 的经验应带入 V2：提交身份要验证，复核证据要可独立重跑，状态规则只在 `AGENTS.md` 定义一次，`accepted` 始终由 Lo 决定。
