## 议题 1：谁来当 watcher？

**结论：本机常驻脚本。**

- GitHub Actions 不行：跑在云端，推不动 Lo 电脑上的 Codex / Claude Code，绕远。
- 各 agent 自己轮询不行：Codex 按额度计费，空转烧额度不划算；且每次唤醒重读上下文开销大。

**落地方案**：Lo 电脑上放一个 `watcher.py`，每 2-3 分钟 `git fetch` 对比 `inbox/` 任务文件的 status 行；Windows 任务计划设开机自启。watcher 只"看"和"喊"，不写仓库。

## 议题 2：通知渠道用什么？

**结论：Windows Toast 为主，本地日志为辅。**

- Lo 就在电脑前，Toast 直达最快。
- 仓库里不放 NOTIFY 文件（污染 git 历史，且有 pull 延迟）。
- watcher 写本地 `watcher.log` 备查；邮件不推荐，不跟报销那条线混。
- 可选项：watcher 触发后由小咩给 Lo 发手机推送，Lo 不在电脑前也能收到。

## 议题 3：怎么防止错误被自动放大？

**结论：熔断三条，写进 watcher 配置。**

1. 同一任务连续触发失败 ≥2 次 → 停掉该任务的自动流转，转人工。
2. 非法状态跃迁（如有人冒写 `accepted`）→ 立即停 + 告警。
3. watcher 自身连续 fetch 失败 ≥5 次 → 退避 + 通知。

每次自动触发写审计日志（谁、何时、干了什么、结果）。兜底的是 Lo，小咩负责把失败现场整理成一页纸，不让 Lo 翻日志。

## 议题 4：无头模式的权限边界？

**结论：按 AGENTS.md §3，现加两条。**

- 可写：`work/claude-code/<任务编号>/`、`evidence/`、status 行、打回的 `review:` 行。
- 不可写：`work/codex/`、他人文件；不得删除文件。
- 新增 ①：无头模式用专用 git 身份 `Claude Code-auto`，审计时一眼区分自动 / 人工。
- 新增 ②：watcher 每次提交后检查 file list，越界自动告警。
- `accepted` 无头模式永远不许碰，代码层面卡死。

## 议题 5：成本对比？

**结论：T001 的真实数据已超阈值，值得做。**

- 今晚 Lo 手动转达 4-5 轮，每轮 3-5 分钟，累计 15-25 分钟人工。
- 阈值建议：**单任务转达 ≥3 轮，或单日人工转达 ≥15 分钟，就值得上 watcher**。T001 已超标。
- 关键：自动化触发的是 Claude Code（DeepSeek，便宜），不烧 Codex 的宝贵额度，反而省钱。

**落地方案**：watcher 先加计数器跑一周（触发次数、失败次数、省掉的人工轮次），用数据决定 V2 是否扩大自动化范围。

## 议题 6：这套东西放哪个仓库？

**结论：另开 `agent-ops`，与 `agent-hq-test` 严格分离。**

- watcher 含本机路径等隐私，不宜进 git；`agent-hq-test` 是流程验证仓库，进了运维脚本就变味。
- watcher 需要的状态机定义从 `agent-hq-test` 的 AGENTS.md 读取，保证单源真相。

**落地方案**：新建私有仓库 `agent-ops`（Lo 建库，小咩搭结构：`watcher/` 脚本 + README 部署说明）。

- 字面上算违反，但 V1 立法本意是"流程没跑通前别乱动"，现在 T001 已闭环，前提满足。
